## 0. 结论先行

DeepCost 是在 **DeepSeek Harness（DSH）** 会话标题栏右侧的用量/余额信息条插件，历经「动态插件原型 → 正式插件化 → 余额疑难问题攻坚」三个阶段，最终以**正式 npm 插件形态**（Host + Client 双端、Typert Remote RPC、Slot UI 注入）交付并开源。

最后卡住许久的「余额不显示」问题，根因是**正式插件 Host 服务缺少 Typert 的 `typertRemote` binding**，导致 Client 的 5 个远程调用**全部静默失败**（`{ok:false}` 不抛错），UI 上表现为「只有谷/出/推荐、唯独没有余额」。解决方式是让服务继承 `TypertRemoteService` 自动挂载 binding，并用**动态插件热挂载**立即生效（免重启），正式修复随下次 DSH 重启自动接管。

## 1. 项目背景与需求演进

### 1.1 初始需求（2026-08-17）

老板（苏明阳）原话：「开发一个插件，上对话上方滚动显示 deepseek 使用量，如果能显示余额更好了。」

### 1.2 需求细化（多轮确认）

| 轮次 | 需求点 | 决定 |
|---|---|---|
| 1 | 显示内容 | 只显示**输出 token + 余额 + 充值链接** |
| 2 | 位置 | 会话标题栏**右上角**（会话列表按钮左侧） |
| 3 | 命名 | **DeepCost**（不用中文名），开源到 GitHub，带配置入口 |
| 4 | 峰谷 | 按 DeepSeek 官方定价显示**峰/谷**（高峰 9-12、14-18 时价格翻倍，其余半价），峰谷本身即官方定价文档链接 |
| 5 | 推荐 | 按任务类型推荐模型：默认 flash（性价比最优），任务复杂需深度推理时推荐 pro（成本差可忽略则 pro 优先）；无明确任务时显示「—」占位 |
| 6 | Gemini | Gemini 会话显示**本月（自然月）累计输出 token**，每月 1 日归零 |
| 7 | 链接 | 余额本身 = 充值链接；峰/谷 = 官方定价文档 |

### 1.3 形态决策：动态插件 → 正式插件

老板批准「那就正式吧」——目标是插件出现在 **Settings → Plugins**、随 DSH 重启存活、用户「用着更放心」。

这决定了技术路线切换：

| 维度 | 动态插件（原型） | 正式插件（交付） |
|---|---|---|
| 加载方式 | 会话内 `cordis_define`/`cordis_run`，进程内存在 | npm 包 + profile `cordis.patch.yml` 声明，随启动加载 |
| Host→Client 通信 | `harness.handle` + `host.call` | **Typert Remote**（`remote.$mount` + `typertGateway` RPC） |
| Client UI | 手写 `__ModuleLoader__.load` bundle | 同（DSH 工具链未开放，手写等价物） |
| 生命周期 | 重启即消失 | 持久 |

## 2. 系统架构

### 2.1 总体结构

```
┌─────────────── 浏览器（Client） ───────────────┐     ┌────────────── DSH 宿主进程（Host） ──────────────┐
│                                                │     │                                                  │
│  __ModuleLoader__.load({id:'deepcost'})        │     │  package.json → exports["."]→ lib/index.js      │
│  ├─ inject: remote/timer/slots                 │     │  DeepCostService extends TypertRemoteService     │
│  ├─ remote.$mount({package, descriptors})      │────▶│  ├─ balance()      → GET /user/balance          │
│  ├─ slots.register(header.utilities, render)   │ RPC │  ├─ sessionModels() → requestHeader().provider  │
│  └─ UsageBar 组件                               │◀────│  ├─ selectModel()   → llm.resolveCallConfig     │
│     ├─ useProjection('tokenUsage')  ← 实时      │     │  ├─ geminiUsage()   → 事件增量折叠            │
│     ├─ useSession(provider)        ← 快照      │     │  └─ recommend()     → v4-flash 提炼任务+推荐    │
│     └─ dcApi.balance() 等           → 远程     │     │                                                  │
└────────────────────────────────────────────────┘     └──────────────────────────────────────────────────┘
```

### 2.2 关键机制

- **Slot 注入**：Client 用 `slots.inject('conversation.session.header.utilities')` + `slots.register({id:'deepcost', order:-100}, render)` 注册信息条；标准 props 提供 `useProjection` / `useSession` / `sessionId`。
- **Typert Remote**：Host 以 `typert.register({package, face:'host', invocations: descriptors})` 注册 5 个 Remote 调用；Client `remote.$mount` 后经 Cordis 子服务 `remote.deepcost` 调用；返回值 `{ok:true, value}` / `{ok:false, error}`。
- **凭据复用**：Host 经 `credentials.resolve('DEEPSEEK_API_KEY')` 解析密钥（支持 `settings` 中 `apiKeyEnv` 自定义名），**密钥绝不下发浏览器**。
- **沙箱**：`curl` 查询以 `danger-full-access` 执行——DSH 沙箱只约束文件效果、不约束网络，此举仅为避免 `workspace-write` 下 curl 子进程被 confine。

### 2.3 部署位置

- 源码/构建产物：`projects/05-DeepCost/`（`src/` 动态插件版，`dist/` 正式插件版）
- 正式安装：`C:\Users\Administrator\.dsh\profiles\node_modules\deepcost\`（copy 同步）
- 组合声明：`C:\Users\Administrator\.dsh\profiles\web\cordis.patch.yml`

## 3. 功能实现

### 3.1 信息条内容（按顺序）

```
[峰|谷] · 出 4.5K · 余额 ¥95.29 · 推荐 v4-flash
```

| 单元 | 逻辑 | 交互 |
|---|---|---|
| 峰/谷 | 北京时间 9:00-12:00、14:00-18:00 = 峰（红），其余 = 谷（绿），每分钟刷新 | 点击 → 官方定价文档 |
| 出 | `useProjection('tokenUsage').outputTokens` 实时投影 | — |
| 本月（Gemini） | Host 增量折叠本月 assistant/message 的 outputTokens，自然月归零 | — |
| 余额 | `balance()` → CNY `total_balance`，60 秒刷新 | 点击 → 充值页 |
| 推荐 | `recommend()` 提炼最近 6 条历史，返回 hasTask/task/model/reason | 点击 → 一键切换模型 |
| 已切换 | 切换成功后显示「已切换 v4-xxx」 | — |

### 3.2 Host 服务（`dist/lib/index.js`）

5 个方法，全部经 Typert Remote 暴露：

1. **balance()**：resolveKey → `curl https://api.deepseek.com/user/balance` → 返回 `{ok, data}`。
2. **sessionModels(args)**：`sessions.get(sid).requestHeader().config` → `{ok, provider, model}`；失败回退 `agentDefaultModel.currentSelection()`。
3. **selectModel(args)**：`llm.resolveCallConfig({provider, model})` → `session.append('request/header')` 切换会话模型。
4. **geminiUsage()**：遍历 live sessions + `sessionQuery` 冷会话，增量折叠本月 Gemini 输出 token（带 `cache` 缓存，每月归零）。
5. **recommend(args)**：取最近 6 条历史 → 调 v4-flash 提炼任务 → 解析 JSON 返回 `{hasTask, task, model, reason}`（含 `reasoning_content` 兜底与正则提取）。

### 3.3 Client 组件（`dist/lib/client.js`）

- `UsageBar`：函数组件，`useSession` 读 provider（快照 `requestConfig`/`provenance` 优先，`sessionModels` 兜底），`useEffect` 定时刷新余额/峰谷/推荐。
- `ErrorBoundary`：class 组件（`React.Component.call(this, props)` 手动继承），渲染异常时显示可见标记而非白屏。
- CSS 变量遵循 DSH 主题 token（`--dsw-alias-*`），自动适配明暗主题。

## 4. 开发过程中的问题与解决

### 4.1 问题清单（按时间）

| # | 问题 | 症状 | 根因 | 解决 |
|---|---|---|---|---|
| 1 | Settings 403 | `/api/settings.describe` HTTP 403 | DSH rc.6 将 settings/credentials RPC 钉在 loopback | 老板加 `--allow-remote-settings`（后随版本移除） |
| 2 | 余额「—」 | 余额查询失败 | pwsh-sandbox + 空 `DSH_PERMISSION_MODE` → workspace-write 沙箱 confine curl | `sandboxPolicy: {mode:'danger-full-access'}` |
| 3 | 推荐不显示 | 推荐空 | v4-flash 是推理模型，`max_tokens:120` 被 reasoning 吃光 | `max_tokens:400` + `reasoning_content` 兜底 + 正则 JSON 提取 |
| 4 | provider 错 | Gemini 会话显示 DeepSeek | `agentDefaultModel.currentSelection()` 是全局默认 | 改用 `session.requestHeader().config.provider` |
| 5 | 峰谷不切换 | 一直红色「峰」 | 时区计算错 | `h=(getUTCHours()+8)%24` |
| 6 | 正式插件搞挂 DSH 启动 | 宿主起不来 | 旧 `typert.register({package, descriptors})` 缺 face/schemas | 新契约 `{package, face:'host', schemas:[], model:{...}, invocations}` |
| 7 | Client bundle 404 | 客户端加载失败 | `exports` 缺 `"./package.json"` | 补上（client-modules 需 `require.resolve('<pkg>/package.json')`） |
| 8 | `$mount` 失败 | remote 挂不上 | strict codec 拒绝 src-json | 全部 codec 改 `{mode:'strict', typeSymbol, schema:{parse:透传}}` |
| 9 | `ctx is not defined` | 组件崩溃 | 组件误用 apply 作用域 ctx | `dcTimer` 经 props 传入 |
| 10 | 信息条不出现 | 只有「DeepCost ✕」 | ErrorBoundary 手写 class 缺 `super(props)` | `React.Component.call(this, props)` |
| 11 | **余额不显示** | 谷/出/推荐在，余额无 | **见 §5（本次核心）** | **见 §5** |

### 4.2 诊断方法论沉淀

- **Badge 陷阱**：把诊断写进 render 函数会被每次重渲染覆盖（badge 永远显示 render 那行）——改用**把诊断直接渲染进 UI 元素**（橙色调试格），一次刷新看到全部状态。
- **会话文件解码**：DSH 会话持久化为**分帧 zstd**（每事件独立压缩帧），需按帧扫描 `ZSTD_MAGIC` + 逐帧 `zstdDecompressSync` 后拼接才能读（`tmp/read-session.cjs`、`scan-session.cjs`）。

## 5. 核心疑难：余额为什么不显示（完整排查链）

这是整个项目耗时最长的问题，值得完整记录。

### 5.1 症状

信息条上**谷、出、推荐全部正常**，唯独**余额永远不出现**（连「余额 —」错误态都没有）。「推荐」看起来在，但后来查明只是「推荐 —」占位符（recommend 也没真正执行）。

### 5.2 排查思路（由表及里）

**第一步：确认底层可用性（一次性排除 3 个假设）**
直接用 pwsh 调 DeepSeek 余额 API → `{"CNY":"97.98"}` 正常返回。
结论：**key 有效、网络通、余额 API 本身没问题。**

**第二步：确认 Host 服务逻辑（宿主进程内直接调用）**
写动态探测插件（`ctx.get('deepcost')` 直接调服务方法）：
- `sessionModels({sessionId})` → `{ok:true, provider:'deepseek-official'}` ✓（任意 sid 格式都能命中）
- `balance()` → `{ok:true, data:{CNY:'97.16'}}` ✓

结论：**Host 服务方法 100% 正常。** 问题必在 Client 端或 Host 的 RPC 网关层。

**第三步：确认 Client 拿到的 provider**
Client 显示 `p:null m:null b:idle` → `isDeep=false` → balance 整块被跳过。
但 Host 直接调用明明能拿到 provider —— 说明 **Client 的远程调用没拿到 Host 的真实返回**。

**第四步：模拟 Client 的 RPC 通道（关键转折）**
走 `typertGateway.invoke()`（Client 调用的真实网关）：
```
RPC sessionModels THROW: typert gateway: deepcost/sessionModels: args must be a plain object
RPC balance       THROW: typert gateway: deepcost/balance: args must be a plain object
```

**第五步：逐层逼近根因**
1. 普通字面量对象（`{args:{...}}`）→ 报「args must be a plain object」（`isPlainObject` 拒绝）
2. **null-proto 对象**（`Object.create(null)`）→ 通过参数校验，但报 **`Service "deepcost" has no visible typertRemote binding`**

**根因确认**：Client 端 `invoke()` 内部构造的 args 本来就是 null-proto（`Object.create(null)`，236 行），传输/接收后正常；真正的问题是 **Host 端 deepcost 服务实例缺少 `typertRemote` binding**。

### 5.3 根因分析

DSH 的 Typert Remote 分两条路由路径：

- **SRC 路径**：遍历 `ctx.reflect.props`，读服务实例的 `typertRemote` 属性（由 `@Remote` 装饰器在编译期注入），再查 `remoteMethods()` 标记。
- **Strict 路径**：`typert.local.get(endpoint)` 直接取严格 descriptor，但**依然要过 `validateBinding()`**——它读 `originalOf(receiver).typertRemote`。

我的手写插件：`DeepCostService extends Service` + `ctx.provide('deepcost', service)`。
- 服务方法**存在且可调**（探测 v5 证明）
- descriptor **注册成功**（探测 v10 证明 `typert.local` 有记录，schema 为 `{parse}` 透传，`JSON.stringify` 显示 `{}` 只是函数不可序列化）
- **唯独 `typertRemote` 属性缺失** → `validateBinding` 抛 `binding-invalid` → **所有远程调用静默失败**（`invokeRpc` 的 catch 返回 `{ok:false, error}`，不抛错、无日志）

这解释了全部现象：`sessionModels` 返回失败 → Client `provider=null` → `isDeep=false` → **余额整块不渲染**；`recommend` 同样失败 → 显示「推荐 —」占位。

### 5.4 解决方案

**正式修复（永久）**：`dist/lib/index.js` 的服务基类从 `Service` 改为 **`TypertRemoteService`**（`@deepseek-ai/dsh-typert-protocol`）：

```js
// 改前
import { Service } from '@deepseek-ai/cordis'
class DeepCostService extends Service {
  constructor(ctx) { super(ctx); ... }
}
// apply 里：ctx.provide('deepcost', service)

// 改后
import { TypertRemoteService } from '@deepseek-ai/dsh-typert-protocol'
class DeepCostService extends TypertRemoteService {
  constructor(ctx) { super(ctx, 'deepcost'); ... }  // 自动注册服务 + 挂 typertRemote binding
}
// apply 里：new DeepCostService(ctx)（不再手动 provide）
```

`TypertRemoteService` 构造时执行 `this.typertRemote = bindTypertRemote(this, this.name)`——binding 就位，网关即可路由。

**热修复（立即生效，免重启）**：Host 端改动需重启才加载，但老板不想重启。用动态插件在宿主进程内直接给**运行中的服务实例**挂 binding：

```js
const ORIG = Symbol.for('cordis.original')
const original = svc[ORIG] || svc            // 剥掉 Cordis proxy，挂到真身
original.typertRemote = Object.freeze({ service: original, serviceKey: 'deepcost', namespace: 'deepcost' })
```

验证：`invokeRpc` 全通——
```
sessionModels → {"ok":true,"provider":"deepseek-official","model":"deepseek-v4-flash"}
balance       → {"ok":true,"data":{...,"CNY":"95.67"}}
geminiUsage   → {"ok":true,...}
```

### 5.5 为什么最终能确认是它（验证闭环）

| 验证项 | 结果 |
|---|---|
| binding 挂载前 `typertGateway.invoke` | ❌ binding-invalid |
| binding 挂载后 `typertGateway.invoke` | ✅ 三个 RPC 全部 `ok:true` |
| 停止热修复插件后 binding 是否还在 | ✅ 还在（binding 挂在服务实例上，不依赖插件存活） |
| 正式代码（继承 TypertRemoteService）本地模拟 | ✅ binding 就位、方法可调（`test-gateway.mjs`） |

两条路都站得住：**当前进程靠热挂载，重启后靠正式代码**。

## 8. 经验与教训

1. **「静默失败」最危险**：`invokeRpc` 对所有错误返回 `{ok:false}` 且不抛错、无日志——任何远程调用异常都会变成「UI 少一块」而毫无线索。诊断时应直接探测**网关层**而非只看 UI。
2. **Host 直接调用 ≠ 远程调用**：服务方法正常不代表 RPC 通。必须模拟 Client 的真实路径（`typertGateway.invoke`）验证。
3. **框架契约必须查源码**：`typertRemote` binding、`isPlainObject` 的 null-proto 要求、strict codec 的 `parse` 校验，全是手写插件踩出的坑——DSH 生态未开放时，文档欠奉，只能读 `node_modules` 里生成/运行时代码。
4. **热修复是运维利器**：宿主进程不可随意重启时，动态 Cordis 插件可安全探测、修补运行中服务（只读/补挂载），验证后再固化到正式代码。
5. **诊断信息要渲染进 UI**：badge 会被重渲染覆盖，debug 元素要画在页面本体上。
